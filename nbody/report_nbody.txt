report_nbody
============

Overview
--------
Benchmark: pyperformance "nbody" (Computer Language Benchmarks Game).
Source kept as nbody/run_benchmark.py (unmodified). Optimized copy:
nbody/optimized/run_benchmark.py. Same five solar-system bodies, same
dt=0.01, same default 20,000 advance() steps.

Purpose: microbenchmark of floating-point pairwise gravity in pure Python.
Each inner step updates velocities for all unordered pairs, then Euler-
integrates positions. The timed loop also calls report_energy() twice per
outer iteration (before and after advance).

Libraries: Python standard library (math in the optimized file) and pyperf
as the timing harness. No numpy / numba.

Data structures (original):
  BODIES dict: name -> ([x,y,z], [vx,vy,vz], mass)
  SYSTEM: list of those triples (shared list objects)
  PAIRS: 10 tuples from combinations(SYSTEM, 2)  (C(5,2)=10)

Algorithm:
  offset_momentum(sun): zero total linear momentum by setting the sun velocity
  advance(dt, n):
    for n steps:
      for each pair (i,j):
        r2 = dx^2+dy^2+dz^2
        mag = dt * r2 ** (-1.5)     # dt / r^3
        vi -= dr * mj * mag
        vj += dr * mi * mag
      for each body: position += dt * velocity
  report_energy: gravitational potential + kinetic energy

N=5 so this is interpreter-bound, not a large-N cache/SIMD problem.
(A 32k-particle C++ kernel from another course is only an idea reference.)

Optimizations
-------------
Still the same 5 bodies, masses, dt, iteration count, and energy
(nbody/verify_energy.py).

Pure-Python experiments (CPython 3.14): replacing ** -1.5 with math.sqrt
and SoA indexing were *slower* here because ** is already specialized and
N=5 is tiny. Unrolling the 10 pairs was only about 3%.

Submitted optimized code (nbody/optimized/run_benchmark.py):
  - numpy structure-of-arrays (float64)
  - numba @njit on advance / energy (C-level loop)
  - mag = dt * inv^3 with inv = 1/sqrt(r2)
JIT is warmed up at import so compile time is outside pyperf measurement.

Dependencies: pip install pyperf numpy numba (script_nbody.sh does this).

Hardware acceleration proposal
------------------------------
Component: pairwise mag = dt / r^3 velocity kick (the body of advance()).

Why: 100% of the useful FLOPs are this kernel. Software opts only remove
CPython overhead. Custom FRSQRT + FMADD is not nbody-specific (ISA example
from the assignment: multiply-accumulate). With N=5 the CPU is interpreter-
bound; HW win appears if the kernel is called from C or N grows.

Implementation: nbody/hw/nbody_force.sv
  Complete FSM + datapath (r2, Quake-style rsqrt seed, two Newton steps,
  inv^3, scale by dt and masses, write dv1/dv2). IEEE-754 binary32 ports,
  valid/ready handshake. FP ops are shortreal stand-ins for hard FPU macros.

Inputs / outputs (all float32 unless noted):
  clk, rst_n                 assumed 200 MHz FPGA-class
  in_valid / in_ready
  dx, dy, dz, m1, m2, dt
  out_valid / out_ready
  dv1x, dv1y, dv1z, dv2x, dv2y, dv2z
Latency: 8 cycles/pair after accept (IDLE..OUT). At 200 MHz ~40 ns/pair
plus SW MMIO. 10 pairs/step -> ~0.4 us compute if fully streamed; real
speedup vs Python is dominated by call overhead unless batched (DMA).

Hardware/software interface:
  Option A — MMIO coprocessor: map registers for dx..dt and dv*; CPU
  writes pair, waits out_valid, adds dv into Python/C arrays.
  Option B — ISA: FRSQRT rd, rs  and  FMADD rd, ra, rb, rc used by a
  C inner loop (or a future CPython C extension). Preferred in an oral
  exam because the ops help other FP kernels.

Block diagram (CPU + accelerator):

                    +------------------+
   Python/C nbody   |  integer core    |
   advance() loop   |  + FPU (optional)|
                    +--------+---------+
                             | MMIO / custom ops
                             v
              +--------------+---------------+
              |         nbody_force          |
              |  in_valid/ready   dx,dy,dz   |
              |  m1,m2,dt                    |
              |  +-----+  +------+  +-----+  |
              |  | r2  |->|rsqrt |->|inv3 |  |
              |  |FMA  |  |Newton|  | *dt |  |
              |  +-----+  +------+  +--+--+  |
              |                      | mag   |
              |           +----------v-----+ |
              |           | scale * m, dr  | |
              |           | dv1, dv2       | |
              |           +----------------+ |
              |  out_valid/ready             |
              +------------------------------+

Performance / area / power:
  + Two Newton iterations: extra area (muls) vs better 1/sqrt accuracy
  + Wider SIMD (4-8 lanes) cuts pairs/cycle, costs register file + ALUs
  + Higher clock needs more pipeline stages and power
  + MMIO for N=5 is overhead-heavy; DMA/ISA pays off for large N
  Estimate: C inner loop + FRSQRT could approach FPU throughput (order
  of 10-50x vs CPython on this microbench). HW vs already-optimized
  Python is smaller until interpreter cost is gone.


Conclusion
----------
Nbody here is a tiny-N Python FP loop. Flattening to SoA and replacing
** -1.5 with 1/sqrt^3 targets the real hotspot without changing physics
(verify_energy.py). The Verilog unit shows how that same 1/r^3 kick maps
to FRSQRT+FMA hardware. Course-grade timing is the QEMU pyperf compare
(>= 7%). Raytrace is the partner's benchmark.
